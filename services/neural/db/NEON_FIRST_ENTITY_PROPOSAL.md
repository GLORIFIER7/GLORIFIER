# Neon first application-data entity proposal

**Status: PROPOSAL ONLY — not a migration and not approved for production.**

## Recommendation

Use a minimal `task_runs` record as the first Neon-owned application entity, if the product owner confirms that retaining task lifecycle metadata is needed. This is the smallest useful entity aligned with the current `POST /v1/tasks` API without storing prompts, model outputs, secrets, or customer content.

Neon remains the application-data store. Supabase remains the separate operational audit sink. Do not mirror records to both systems.

## Proposed data contract

| Field | Proposed type | Purpose | Constraints |
| --- | --- | --- | --- |
| `id` | `uuid` | Internal task-run identifier | Primary key, generated by the application |
| `request_id` | `uuid` | Correlates with API request and audit event | Required; indexed; not an authorization credential |
| `action_class` | `text` | Policy/action category | Required; bounded length; validate against application policy |
| `status` | `text` | Execution outcome | Required; allowlist only |
| `provider` | `text` | Provider label, when known | Nullable; allowlist or bounded value |
| `evidence` | `jsonb` | Small, sanitized evidence codes | Optional; bounded item count and size; no prompt/output/credentials |
| `created_at` | `timestamptz` | Record creation time | Required; UTC |
| `expires_at` | `timestamptz` | Retention deadline | Required only after retention is approved; indexed for cleanup |

This proposal intentionally excludes raw prompts, model responses, API tokens, authorization headers, wallet data, payment details, and unrestricted request bodies.

## Decisions required before a migration

1. **Ownership / tenancy:** the current API uses a single server-side bearer token and does not establish a customer or tenant identity. Do not invent an `owner_id` or claim tenant isolation until an authenticated ownership model exists.
2. **Retention:** choose a retention period and deletion mechanism before adding `expires_at` or automated cleanup. A default period is not approved by this document.
3. **Write semantics:** decide whether task records are created before execution, after execution, or through an outbox. Do not implement a second database write in a way that can silently diverge from the Supabase audit sink.
4. **Failure policy:** decide whether Neon unavailability should block task execution. The current endpoint's audit behavior is fail-closed when Supabase audit persistence is enabled; this proposal does not change that behavior.
5. **Access model:** define separate least-privilege runtime and migration roles, TLS requirements, indexes, backup/restore, and staging verification.
6. **Sensitive data review:** confirm that `action_class`, provider labels, and evidence codes cannot contain user-supplied content or secrets.

## Safe implementation sequence

1. Approve or revise this data contract.
2. Implement a disabled-by-default Neon repository interface and unit tests using fake connections; no network calls in unit tests.
3. Add a versioned SQL migration with constraints and indexes, but do not apply it to any live database.
4. Test migration and rollback on a disposable or confirmed staging database after verifying backup/restore.
5. Verify least-privilege permissions, retention/deletion, and sanitized failure behavior.
6. Enable in staging only after explicit configuration and evidence review. Production enablement requires a separate approval.

## Current verified boundary

The repository currently has an opt-in Neon connectivity probe that runs TLS-protected `SELECT 1`; it does not create schemas or write application records. A successful connectivity probe proves connectivity only, not application-data readiness. No migration, live connection, production write, or deployment is performed by this proposal.
